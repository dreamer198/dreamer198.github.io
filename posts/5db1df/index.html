从本地文件夹到 GitHub 新仓库：一步步推送指南

发表于2025-11-06|更新于2026-09-29|开发工具
|总字数:1.3k|阅读时长:5分钟

本文记录如何把本地已有的项目文件夹推送到一个全新的 GitHub 仓库。整个流程是：本地初始化并提交，在 GitHub 创建一个空仓库，添加远程地址，首次推送。

前置条件

  • 已安装 Git（Linux），可以用 git --version 确认；
  • 有 GitHub 账号；
  • 可选：安装 GitHub CLI（gh），用命令行创建仓库。

二、在 GitHub 创建一个空仓库

创建仓库时不要勾选自动生成 README、.gitignore 和 License，让远程仓库完全为空，第一次推送才不会冲突。

网页创建：打开 https://github.com/new，填写仓库名（例如 your-repo），选择 Public 或 Private，不勾选 README / .gitignore / License，点击 Create repository。创建成功后页面会显示 HTTPS 和 SSH 两种远程地址，任选其一。

五、日常使用

常见问题

现象 原因 处理方法
推送被拒绝：rejected non-fast-forward 远程不是空仓库，可能自动生成了 README 等文件 执行 git pull --rebase origin main 后再 git push
Permission denied (publickey) SSH Key 没有配置好或没有添加到 GitHub 用 ssh -T git@github.com 自查，确认公钥已添加
每次都要输入账号和 Token 使用 HTTPS 推送时，GitHub 要求 Token 代替密码 改用 SSH
大文件推不动、仓库体积过大 提交了数据集、可执行文件或编译产物 不提交这类文件，必要时使用 Git LFS

六、提交信息规范（推荐）

为了让提交历史更清晰、可搜索，推荐遵循 Conventional Commits 规范：

基本格式：

常用类型一览：

类型 用途 示例
feat 新功能（feature） feat(bt): add new takeoff behavior
fix 修复 bug fix(mavros): correct FCU URL parsing
chore 非功能改动（构建脚本、依赖、初次提交） chore: initial commit
docs 文档修改 docs: update README with usage example
style 代码格式（不影响功能） style: reformat indentation in ListenCommand.cpp
refactor 重构（非修复非新增） refactor(bt): simplify tick logic
test 测试相关改动 test: add unit test for JSON parser
perf 性能优化 perf(nav): improve GPS update rate
build 构建系统或依赖更改 build: switch to CMake 3.22
ci CI 配置更改 ci: add GitHub Actions workflow

几点补充：scope 可选，用来指明影响范围（例如模块名 bt、mavros、nav、planner）；正文可以写改动的动机、做法和影响面，方便代码评审和后续排查；页脚写 Closes #123 或 Refs #123 可以关联问题单；有破坏性变更时在页脚用 BREAKING CHANGE: 说明迁移方法。

小结

流程的关键是：本地初始化并提交，创建空的远程仓库，添加远程地址，首次推送。长期使用建议选 SSH，省去反复认证；.gitignore 要在第一次提交前写好。
